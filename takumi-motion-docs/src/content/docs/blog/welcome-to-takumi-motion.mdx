Generating animated README banners, social cards, or release previews in CI usually means spinning up a headless browser. Chromium brings heavy cold-start overhead, subtle font-hinting differences across machines, and frame-timing drift that makes byte-exact caching impossible.

We built Takumi Motion (`1.1.0`) to render React trees, declarative recipes, or raw HTML directly into GIF, WebP, APNG, sprite sheets, and stills using a native Rust rasterizer.

## The Goal

We wanted an animation engine where every frame is a pure function of `(frame, props)`—producing identical output bytes whether rendered serially on a laptop, across a worker pool in CI, or audited inside a publishing pipeline.

## The Architecture

Takumi Motion connects high-level authoring (`takumi-motion/react`, `takumi-motion/recipes`, or raw HTML) to `@takumi-rs/core`, a prebuilt native Rust layout and rasterization module, through a six-stage pipeline (`AUTHOR`, `PLAN`, `CAPTURE`, `COMPILE`, `RASTER`, `ENCODE`).

## What it cost

Guaranteeing byte-identical output across serial and parallel worker runs meant banning ambient side effects during capture. Components read `useFrame()` instead of `Date.now()`, `Math.random()` is shimmed per frame index, and analytical springs expose `springSettleFrames` so `TM_TRANSITION_UNSETTLED` catches animations that outlive their scene window.

<Aside type="caution" title="Limitations">
Because there is no browser engine in the pipeline, Takumi Motion supports a bounded CSS property set (`SUPPORTED_STYLE_PROPS`, checked by `TM_UNKNOWN_STYLE_PROP`) rather than arbitrary browser DOM features like WebGL, `<video>`, or `<canvas>` elements. Fonts must also be vendored locally as TTF/OTF files rather than fetched over the network (`TM_FONT_NETWORK`).
</Aside>

## Getting started

```bash
pnpm add takumi-motion @takumi-rs/helpers
pnpm exec takumi-motion check src/banners/readme.tsx
```
